# प्रमाण सेतु · Praman Setu
**The proof is already in Sewa Setu.** An AI evidence assistant for the officers who decide caste and domicile certificates on Chhattisgarh's Sewa Setu portal.

Built for the **Sewa Setu Innovation Hackathon** (Government of Chhattisgarh / CHiPS with IIIT Naya Raipur), Problem Statement 1: AI and Automation, 28 September 2026.

> Hackathon prototype. Not an official Government portal. All citizen data is **synthetic**. Sewa Setu MIS figures are real public data, fetched 27-09-2026.

## The problem, from Sewa Setu's own public MIS
- 53.9 lakh applications since April 2025, 95.7% decided on time.
- **Caste certificates: 22% of applications but 61% of the 3.64 lakh rejections** (about 1 in 5 caste applications rejected). Income certificates: 1.4%.
- The officer console has a decision/checklist tab that is empty. There is no way to look up a relative's earlier certificate, even though Rule 3(3) of the 2013 rules accepts it as evidence, and a Chhattisgarh High Court order (July 2026) says pre-1950 papers are not needed in every case where family members hold certificates.

## What Praman Setu does
1. **Kendra pre-check:** before the fee is paid, finds a parent's or sibling's certificate in the archive. It can also search the applicant's native (maiden) village.
2. **Officer evidence panel:** side-by-side comparison across spellings and scripts, validity checks (permanent, competent authority, not cancelled, category), and a same-family / not-this-family confirmation with grounds. **The officer always decides.**
3. **Reasoned orders and notices:** a numbered order citing only records, a hearing before any rejection, and a plain-Hindi citizen message checked against the records.
4. **Collector view:** real MIS analytics at district level, with pilot targets and stop rules. There is no officer ranking.

It never auto-rejects. "No record found" is never a reason to reject. Caste is never inferred from surnames. Data stays in the State Data Centre.

## Run locally (offline)
```bash
bash app/backend/run.sh                  # API on http://localhost:8000 (first run builds data + model)
npm --prefix app/frontend install
npm --prefix app/frontend run dev        # UI on http://localhost:5173 (proxies /api)
```
Open `http://localhost:5173/?demo=reset`. The demo script is in `app/iterations/round5_changes.md`. The frontend also runs without the backend, using bundled fixtures.

Tests: `cd app/backend && uv run pytest -q` (80 passing). Build: `npm --prefix app/frontend run build`.

## Model (synthetic, held-out evaluation)
| Slice | Precision (strong) | Recall (strong) |
|---|---|---|
| Overall | 0.89 | 0.48 |
| Women applicants | 0.88 | 0.33 |
| Women, with native-village search (upper bound) | 0.90 | 0.71 |

The data is generated by us, so real accuracy is what a 6-week study and a 90-day shadow pilot would measure (target: 98% precision on officer-confirmed matches).

## Limitations
See `LIMITATIONS_ANALYSIS.md`. Summary:
- no OCR of scans yet;
- real-record accuracy is unknown;
- land and ration records are mocked (they need a Revenue order);
- there is no live Sewa Setu integration (the console is a simplified redraw from a public walkthrough).
